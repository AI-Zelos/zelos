# Kubernetes 花了 8 年才等来它的 CNCF。AI Agent 的"操作系统"还没出现。

上篇聊了 PR 要不要被替代，这篇聊一个更大的问题。

---

先问一个问题：

**2025 年，一个公司部署了 50 个 AI Agent 在生产环境。谁在管它们？怎么管？**

我问过几个做 AI 平台的朋友，诚实的回答基本都是：

> "我们在用 FastAPI + Redis + Celery 自己写的调度器。"

这让我想起 2014 年。那时候大家都在用 shell 脚本 + Supervisor 管理容器。Docker 刚出来，但没人知道 Kubernetes 会成为标准。

**2025 年的 AI Agent 管理，就是 2014 年的容器管理。**

---

## 三个行业缺位

现在的 AI 基础设施有三个巨大的洞：

**第一个洞：Agent 之间的通信有一堆协议（MCP、A2A），但谁来治理它们？**

MCP 让 Agent 能调 GitHub。A2A 让 Agent 能互相发现。但谁来决定"这个 Agent 可以调 GitHub 但不可以 force push"？谁在 Agent 调用了一个不应该调用的 API 时拦下来？

协议层只解决"能通信"，不解决"能信任"。中间缺了一层 **Governance Layer**。

**第二个洞：Agent 框架越来越多了，但都在抢"怎么 build Agent"这块地。**

LangGraph、CrewAI、AutoGen、OpenAI Agents SDK——他们都在竞争谁能让开发者更快地搭出来一个 Agent。这是 2015 年"谁做更好的 MVC 框架"的翻版。

但真正的问题不是"怎么搭 Agent"。真正的问题是：**当你有 50 个 Agent 在生产环境同时跑，你信得过它们吗？**

Build 的问题已经差不多被解决了。Govern 的问题还没人认真做。

**第三个洞：整个行业的"AI 写代码"产能爆炸了，但"AI 写完代码之后怎么办"这个链路是空的。**

Cursor、Copilot、Claude Code 能在几分钟内写出几千行代码。然后呢？谁 Review？谁测试？谁决定能不能上线？

所有的工具都在做"**生成**"。没有人做"**验证**"和"**决策**"。

---

## 我在做的一件事

我们做了一个开源项目，叫 **Zelos**。它做的事情很简单：

**不帮你写 Agent。帮你治理 Agent。**

具体来说：

1. **管执行**：Goal 丢进来 → 自动拆成 Task → 按能力匹配 Agent → 调度执行 → 超时重试、心跳检测
2. **管验证**：Agent 跑完不是"Done"，是"Done + 证据"。测试结果、安全扫描、Benchmark 数据全部收集，算一个置信度
3. **管决策**：置信度 97% + 低风险 → 自动上线。置信度低于 40% → 自动驳回。中间地带 → 推给人审批

如果你熟悉 Kubernetes 的类比：**Kubernetes 管的是 Pod 的调度、自愈、滚动升级。Zelos 管的是 Agent 的调度、验证、决策。**

Agent 框架 = Docker（建东西的）。Zelos = Kubernetes（管东西的）。

---

## 为什么现在没有人做这个？

因为还不够痛。

大多数团队现在用的 Agent 不超过 3 个。3 个 Agent 你确实不需要治理层——batch script 就够了。

但 50 个呢？500 个呢？

当 Agent 数量超过一定阈值，就会出现几个现象：

- **调度复杂度指数增长**：哪个 Agent 做哪个任务、什么时候做、失败了切给谁——不是人脑能手动管的
- **验证必须自动化**：你不可能逐个看 500 个 Agent 的输出
- **决策必须有依据**："能不能上线"不能凭感觉。要有证据、有分数、有规则

这些现在还不需要。但三年后一定会需要。

---

## 很多人问"你们和 LangGraph 有什么区别"

不是竞争对手。**我们是不同的层。**

LangGraph 帮你定义 Agent 的执行逻辑（条件分支、循环、工具调用）。Zelos 帮你治理部署后的 Agent（谁来做、怎么做验证、能不能信任）。

如果硬比：

| | LangGraph / CrewAI | Zelos |
|---|---|---|
| 定位 | Agent 构造工具 | Agent 治理平台 |
| 帮谁 | Agent 开发者 | 技术管理者、平台团队 |
| 管什么 | Agent 怎么执行 | Agent 跑完了能不能信 |
| 类比 | Spring / Django | Kubernetes |

可以这样理解：你用 LangGraph 写 Agent，然后注册到 Zelos 上跑。写是写的事，治是治的事。

## 这个项目的现状

**v1.0.0，开源（Apache 2.0），151 个自动化测试，已发布 PyPI。**

它还很年轻。但我们已经跑通了论文里定义的 CP 治理范式（Change Proposal），实验数据是真实的：返工率从 35% 降到 5%，人工依赖度从 100% 降到 0%。

我们的目标不是做"又一个 Agent 框架"。我们的目标是定义 AI Agent 时代的 Governance Layer。

## 一个预测

未来三年的 AI 基础设施格局会变成这样：

```
Layer 1: Agent 构造（LangGraph, CrewAI, AutoGen）
   ↓
Layer 2: Agent 治理（Zelos 想做的东西）
   ↓
Layer 3: Agent 市场 / 编排 / 订阅
```

Layer 1 已经卷成红海。Layer 3 还很远。**Layer 2 是空白的。**

谁先定义它，谁就定义了一个时代的基础设施。

就像 Kubernetes 定义了容器编排，Git 定义了版本控制，Linux 定义了 OS 内核——**伟大的基础设施项目，都是在一个还没人定义过的层上，第一个把标准立起来。**
