# 08 — Change Approval Request (CAR)

## PR is Dead. Long Live CAR.

The traditional Pull Request was designed for humans writing hundreds of lines. It cannot handle AI producing 40,000-line changes.

**CAR (Change Approval Request) is the replacement.** It shifts the review target from code to change.

## CAR Structure: 10 Mandatory Modules

1. **Intent** — What problem? What is out of scope?
2. **Requirement Mapping** — Every code change traces to a requirement
3. **Architecture Delta** — What changed in the system?
4. **Implementation Plan** — Steps, phases, migration strategy
5. **Impact Analysis** — All affected modules, APIs, DB, events
6. **Evidence** — Tests, benchmarks, security, coverage — quantified
7. **Risk Assessment** — Level, cause, impact, mitigation
8. **Rollback Plan** — Steps, estimated downtime, verification
9. **Generated Artifacts** — API diffs, migration scripts, reports
10. **Human Decision** — Architecture/Business/Risk/Deployment decisions

## Generation: Automated, Not Manual

CAR is **auto-generated by the Runtime pipeline**:

```
Planner Agent   → Intent + Plan + Architecture Delta
Code Agent      → Code diff
Test Agent      → Test results + coverage
Security Agent  → Vulnerability report
Perf Agent      → Benchmark data
        ↓
Runtime aggregates → Complete CAR
```

Humans only need to **review and decide**. The Runtime does the assembly.

## Review Roles

One CAR, multiple review perspectives:

| Role | Reviews |
|------|---------|
| Product | Intent: business goals, scope |
| Architect | Architecture Delta: system impact |
| Tech Lead | Implementation Plan, code correctness |
| QA | Evidence: test coverage, regression |
| Security | Security scan results |
| SRE | Risk, Rollback, deployment strategy |

## Enforcement

- **All 10 modules are mandatory** — missing any → rejection
- **No "LGTM"** — review must state explicit decision
- **No vague evidence** — "tests passed" is insufficient
- **No deployment without rollback** — risk ≥ medium requires plan
