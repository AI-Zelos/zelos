# Zelos v0.9.0 需求规格说明书

> 核心主题：**Change Evidence Package** — 让 Zelos 从执行引擎升级为治理平台。
>
> 参考文档：
> - `docs/blueprint/change-evidence-package.md` — 概念蓝图
> - `docs/v0.8.0-requirements.md` — 上一版本需求

---

## 一、为什么要做 v0.9.0

### 1.1 现状（v0.8.1）

当前 Zelos 回答的是：

> **"Agent 能不能执行这个 Goal？"**

它能做到：

- 接收 Goal → Planner 分解 Task DAG → Scheduler 调度 → Agent 执行 → 返回 Artifact → Done
- 崩溃恢复、重试、心跳超时、不可重试错误
- 审计日志记录操作行为
- 事件链可重建 Goal 状态

但它**做不到**的事，恰恰是生产环境最需要的：

| 缺失 | 后果 |
|------|------|
| Agent 执行完一个 Task，输入上下文和输出 Artifact **不入事件、不入存储** | 出问题后无法回溯"Agent 当时收到了什么，产出了什么" |
| 没有统一的执行链路查询 API | 用户想知道"这个 Goal 从提交到完成，每一步发生了什么"，需要手动拼多个 API |
| Planner 只输出 Task 列表，不输出**架构影响分析** | 不知道这次变更会影响哪些模块、新增什么依赖、风险多大 |
| Verifier 验证了 Schema，但**验证结果不归并** | 每个 Task 的验证各自独立，没有整体的证据汇总 |
| Policy 只做成本/速率限制，不做**基于证据的批准决策** | 高风险变更和低风险变更走同一套流程 |

### 1.2 目标状态

v0.9.0 的 Zelos 回答的是：

> **"Agent 执行的这次变更，值不值得被接受？"**

核心产出不再是"一堆 Agent 产出的 Artifact 散落各处"，而是一份结构化的 **Change Evidence Package（变更证据包）**：

```
Intent         — 为什么做这次变更？人要确认什么？
Architecture Delta — 系统结构发生了什么变化？
Impact Analysis    — 影响了哪些接口、数据模型、依赖？
Evidence           — 测试结果、Benchmark、安全扫描、回归结果
Risk & Rollback    — 风险评级、回滚方案
Confidence         — 综合置信度评分
Execution Trace    — 完整的执行链路（输入/输出/时序）
```

人的角色从 **Code Reviewer** → **System Governor（系统治理者）**。

## 二、需求清单

### REQ-01：完整的 Task 生命周期事件（P0）

#### 背景

当前 EventBus 的应用非常有限：
- `task.started` / `task.completed` / `task.failed` **从未被 publish**
- 只有 `scheduler.evaluate_retry()` publish 了 `task.retry_scheduled`
- AuditLogger 记录了操作行为，但 AuditLog ≠ Event，不在事件链中

**没有完整的 Task 生命周期事件，就没有完整的执行链路可查。**

#### 需求描述

1. `ExecutionEngine.dispatch()` → publish `task.started` 事件，payload 包含：
   - `task_id`, `agent_id`, `agent_name`, `required_capability`
   - `input_context` — ContextAssembler 组装的完整输入上下文
   - `timestamp`

2. `ExecutionEngine.submit_result()` → publish `task.completed` 或 `task.failed` 事件，payload 包含：
   - `task_id`, `agent_id`
   - `output_artifact` — Agent 返回的完整 artifact（`task.completed` 时）
   - `error` — 错误信息（`task.failed` 时）
   - `duration_ms` — 执行耗时
   - `timestamp`

3. `TaskGraphEngine.transition()` — 所有状态变迁自动 publish 对应事件：
   - `task.created` — 含 `description`, `required_capability`, `dependencies`, `priority`, `timeout_ms`
   - `task.ready` — task 变为 READY
   - `task.assigned` — task 分配给 agent

4. 所有 Task 事件使用 `goal_id` 作为 `correlation_id`，支持按 Goal 维度查询。

#### 大数据量考虑

- 事件 payload 中的 `input_context` 和 `output_artifact` 可能很大（数 MB）
- **策略**：大 payload 写入 `StorageBackend`，事件只存引用（`content_ref`），按需加载
- `InMemoryEventStore` 的 max_events 限制需对超大 payload 做截断或外存

#### 验收标准

- [ ] `task.started` 事件被 publish，payload 含 `input_context`
- [ ] `task.completed` 事件被 publish，payload 含 `output_artifact` + `duration_ms`
- [ ] `task.failed` 事件被 publish，payload 含 `error` + `duration_ms`
- [ ] 所有 Task 事件 `correlation_id == goal_id`
- [ ] 大 payload（>100KB）写 StorageBackend，事件只存引用
- [ ] `tests/test_task_lifecycle_events.py` 覆盖上述场景

### REQ-02：Execution Trace API（P0）

#### 背景

当前 `get_goal_status()` 返回的是 Goal 的**当前状态快照**，不是执行链路。用户无法知道：

- 每个 Task 什么时候被创建、调度、执行、完成
- 每个 Task 收到了什么输入、产出了什么输出
- 整个 Goal 执行了多长时间

#### 需求描述

1. 新增 `Runtime.get_goal_trace(goal_id) → ExecutionTrace` 方法。

2. `ExecutionTrace` 数据结构：

```python
@dataclass
class ExecutionTrace:
    goal_id: str
    goal_description: str
    status: str
    total_duration_ms: float
    tasks: list[TaskTrace]

@dataclass
class TaskTrace:
    task_id: str
    description: str
    required_capability: str
    agent_id: str | None
    agent_name: str | None
    status: str
    attempt: int
    timeline: list[TraceEvent]
    input_context: dict | None      # 按需加载
    output_artifact: dict | None    # 按需加载
    error: dict | None

@dataclass
class TraceEvent:
    event_type: str        # task.created / task.started / task.completed / task.failed / task.retry_scheduled
    timestamp: float
    payload: dict
```

3. 实现方式：从 EventBus 按 `correlation_id == goal_id` 拉取所有事件，按时间线排序，归并成 `ExecutionTrace`。

4. `input_context` 和 `output_artifact` 默认不展开（`None`），传 `include_artifacts=True` 时从 StorageBackend 按需加载。

#### 大数据量考虑

- 一个 Goal 可能有几百个 Task，每个 Task 的事件链可能很长
- **策略**：`get_goal_trace(goal_id, limit=50, offset=0)` 支持分页
- 默认只返回最近 50 个 TaskTrace，避免一次加载过多数据
- `timeline` 默认只返回关键节点（created → started → completed），详细信息按需展开

#### 验收标准

- [ ] `get_goal_trace(goal_id)` 返回完整的执行链路
- [ ] 每个 TaskTrace 包含完整的时间线
- [ ] `include_artifacts=True` 时加载输入/输出
- [ ] 分页 `limit/offset` 正常工作
- [ ] 未完成的 Goal 也能查询（trace 到当前时刻）
- [ ] `tests/test_execution_trace.py` 覆盖：单 Task / DAG 多 Task / 重试中 / 大 payload 按需加载

### REQ-03：Intent Specification（P1）

#### 背景

当前 `submit_goal(description="实现登录")` 的描述太自由。Agent 可能理解偏了，执行完才发现需求不对。

Intent Spec 的作用是：在 Agent 动手之前，让人和 Agent 对"要做什么、成功标准是什么"达成共识。

#### 需求描述

1. `submit_goal()` 新增可选参数 `intent: IntentSpec | None`：

```python
@dataclass
class IntentSpec:
    description: str            # 自然语言描述
    success_criteria: list[str] # 可验证的成功标准
    constraints: list[str]      # 约束条件
    scope: str = "auto"         # auto | single_module | multi_module | system_wide
    rollback_on_failure: bool = True
```

2. 如果提供了 `IntentSpec`，Planner 在规划前先输出 `IntentConfirmation`：
   - 确认理解的需求
   - 确认的约束
   - 预计的 Task 数量和依赖关系
   - 不确定的部分（标记为 `need_clarification`）

3. 新增 `confirm_intent(goal_id, confirmed=True, clarifications=...)` → 人确认后 Planner 才真正开始规划。

4. 如果**没有**提供 `IntentSpec`，Runtime 保持向后兼容——按现有流程直接规划执行。

#### 验收标准

- [ ] `submit_goal(intent=IntentSpec(...))` 正常接受
- [ ] Planner 输出 `IntentConfirmation`，含确认的需求和约束
- [ ] `confirm_intent()` 之后 Planner 才真正规划
- [ ] 没有 IntentSpec 时保持向后兼容
- [ ] `tests/test_intent_spec.py` 覆盖上述场景

### REQ-04：Architecture Delta（P1）

#### 背景

当前 Planner 只输出 Task 列表（"做什么"），不输出"改了哪里"。人无法评估变更的影响范围。

#### 需求描述

1. `PlannerPlan` 新增 `architecture_delta: ArchDelta | None` 字段：

```python
@dataclass
class ArchDelta:
    modified_modules: list[str]       # 修改的模块/服务
    new_dependencies: list[str]       # 新增依赖
    removed_dependencies: list[str]   # 删除的依赖
    api_changes: list[APIChange]      # API 变更
    data_model_changes: list[str]     # 数据模型变更
    risk_level: str                   # low | medium | high | critical
    explanation: str                  # 为什么这么设计
```

2. `ArchDelta` 在 Planner 规划阶段生成，作为 `ExecutionPlan` 的一部分。

3. 如果 Planner 无法推断架构影响，标记 `risk_level = "unknown"`，require_human。

#### 大数据量考虑

- 大规模变更可能涉及数百个模块
- **策略**：`modified_modules` 限制最多 200 条目，超出的归并到 `...and N more`

#### 验收标准

- [ ] Planner 生成的 Plan 包含 `ArchDelta`（或标记为 unknown）
- [ ] `ArchDelta.modified_modules` 包含变更的模块列表
- [ ] `risk_level` 正确推断（或为 unknown）
- [ ] `tests/test_architecture_delta.py` 覆盖上述场景

### REQ-05：Evidence Collection Framework（P1）

#### 背景

当前每个 Agent 返回的 Artifact 是零散的。没有人把这些结果**归并成一个整体的证据视图**。

"测试过了"、"安全扫描过了"——这些证据应该被 Runtime 收集、归类、汇总，而不是散落在各个 Task 的 artifact 里。

#### 需求描述

1. Agent SDK 新增 `Evidence` 输出类型：

```python
@dataclass
class Evidence:
    type: str           # test_result | benchmark | security_scan | api_diff | canary | custom
    tool: str           # pytest | wrk | bandit | openapi-diff | ...
    result: str         # PASS | FAIL | WARN | SKIP
    data: dict          # 详细数据（passed/failed counts, metrics, etc.）
    summary: str        # 人类可读摘要
```

2. `ExecutionResult` 新增 `evidence: list[Evidence]` 字段：

```python
class ExecutionResult:
    status: str         # completed | failed
    artifact: Artifact
    evidence: list[Evidence]   # v0.9.0 新增
```

3. Runtime 在收集完所有 Task 的 result 后，归并成 `EvidenceBag`：

```python
@dataclass
class EvidenceBag:
    goal_id: str
    items: list[Evidence]           # 所有 Task 产生的证据
    summary: dict[str, EvidenceSummary]  # 按 type 汇总
    all_pass: bool                  # 是否全部 PASS
    failed_items: list[Evidence]    # 失败的证据项
```

4. `ExecutionReport` 自动包含 `EvidenceBag`。

#### 大数据量考虑

- 一个 Goal 可能有几百条 Evidence
- **策略**：`EvidenceBag.items` 按 type 分组存储，查询时按需展开
- 大量同类型 Evidence 做聚合（如 100 个 task 的 test_result → 汇总成 1 条）

#### 验收标准

- [ ] Agent 可以返回 `Evidence` 列表
- [ ] Runtime 归并所有 Task 的 Evidence 成 `EvidenceBag`
- [ ] `EvidenceBag.all_pass` 正确判断
- [ ] 同类型 Evidence 自动聚合
- [ ] `tests/test_evidence_collection.py` 覆盖上述场景

### REQ-06：Confidence Scoring（P1）

#### 背景

即使所有 Task 都完成了，人也需要判断：这次变更质量怎么样？敢不敢上线？

`ConfidenceScorer` 基于收集到的 Evidence 计算一个 0.0-1.0 的置信度分数，给人一个客观的决策参考。

#### 需求描述

1. 新增 `ConfidenceScorer` 插件接口：

```python
class ConfidenceScorer(ABC):
    @abstractmethod
    def score(self, evidence: EvidenceBag, arch_delta: ArchDelta) -> ConfidenceResult: ...

@dataclass
class ConfidenceResult:
    score: float                # 0.0 - 1.0
    breakdown: dict[str, float] # 各项得分明细
    recommendation: str         # approve | reject | need_human
    reasoning: str              # 为什么给出这个分数
```

2. 默认实现：`WeightedConfidenceScorer` — 加权评分。

```yaml
# zelos.yaml
confidence:
  weights:
    test_pass: 0.30        # 测试全部通过
    benchmark: 0.15        # 性能不下降
    security: 0.20         # 安全扫描通过
    api_compat: 0.10       # API 向后兼容
    canary: 0.15           # 金丝雀通过
    code_review: 0.10      # 代码审查通过
  thresholds:
    auto_approve: 0.95     # ≥0.95 自动通过
    require_human: 0.70    # <0.70 强制人审
    auto_reject: 0.40      # <0.40 自动拒绝
```

3. `ConfidenceScorer` 在 `ExecutionReport` 生成时被调用。

4. 如果没有任何 Evidence，`score` 返回 0.0，`recommendation = "need_human"`。

#### 验收标准

- [ ] `WeightedConfidenceScorer` 根据 Evidence 计算分数
- [ ] 分数在 0.0-1.0 之间
- [ ] 权重可通过 `zelos.yaml` 配置
- [ ] 无 Evidence 时 `score=0.0, recommendation=need_human`
- [ ] 阈值（auto_approve / require_human / auto_reject）生效
- [ ] `tests/test_confidence_scorer.py` 覆盖上述场景

### REQ-07：Execution Report（P0）

#### 背景

这是 v0.9.0 的**核心交付物**。所有 REQ-01 到 REQ-06 的能力，最终都汇聚到 `ExecutionReport` 中。

`ExecutionReport` 是 Goal 完成后的统一输出——一份结构化的"变更证据包"，让人可以在不读代码的情况下做出批准/拒绝决策。

#### 需求描述

1. 新增 `ExecutionReport` 数据结构：

```python
@dataclass
class ExecutionReport:
    goal_id: str
    status: str                             # completed | failed | cancelled

    # ── Intent ──
    intent: IntentSpec | None
    intent_confirmed: bool

    # ── Architecture Delta ──
    architecture_delta: ArchDelta | None

    # ── Execution Trace ──
    trace: ExecutionTrace

    # ── Evidence ──
    evidence_bag: EvidenceBag

    # ── Confidence ──
    confidence: ConfidenceResult

    # ── Risk & Rollback ──
    risk_level: str                         # low | medium | high | critical
    rollback_plan: RollbackPlan | None

    # ── Summary ──
    changed_files: int                      # 变更文件数（如果可统计）
    total_duration_ms: float
    created_at: float
    completed_at: float | None

@dataclass
class RollbackPlan:
    strategy: str           # event_sourcing_replay | manual | none
    restore_to_event_position: int | None
    estimated_downtime_s: float
    steps: list[str]
```

2. 新增 `Runtime.get_execution_report(goal_id) → ExecutionReport` API。

3. `wait_for_goal()` 在 Goal 终态时自动返回 `ExecutionReport`（向后兼容：旧 `get_goal_status()` 保持不变）。

4. `ExecutionReport` 自身是一个 **stamped event**：`execution_report.created` 事件写入 EventBus，可被回放、审计。

#### 大数据量考虑

- `ExecutionReport` 包含完整的 trace + evidence，可能很大
- **策略**：
  - `trace.tasks[].input_context` 和 `output_artifact` 默认 lazy-load
  - `evidence_bag.items` 默认聚合，详情按需展开
  - 支持 JSON 序列化和分块存储

#### 验收标准

- [ ] `get_execution_report(goal_id)` 返回完整的 ExecutionReport
- [ ] Report 包含 Intent、ArchDelta、Trace、Evidence、Confidence、RollbackPlan
- [ ] `wait_for_goal()` 在 Goal 终态时返回 ExecutionReport
- [ ] `execution_report.created` 事件写入 EventBus
- [ ] Report 可 JSON 序列化/反序列化
- [ ] `tests/test_execution_report.py` 覆盖：完整报告 / 部分数据缺失 / 大 payload

### REQ-08：Policy Gate v2 — 基于证据的自动决策（P2）

#### 背景

当前 Policy 只做 CostLimit / RateLimit / Allowlist——这些是执行前的过滤。

v0.9.0 的 Policy Gate v2 是基于**执行后的证据**做决策——要不要批准这次变更？

#### 需求描述

1. 新增 `PolicyGate` 插件接口：

```python
class PolicyGate(ABC):
    @abstractmethod
    def evaluate(self, report: ExecutionReport) -> GateDecision: ...

@dataclass
class GateDecision:
    action: str             # auto_approve | auto_reject | require_human
    reason: str
    required_approvers: list[str]  # 如果 require_human，需要谁来批
```

2. 默认实现：`EvidenceBasedPolicyGate`，基于 `zelos.yaml` 中的规则：

```yaml
policy_gate:
  rules:
    - if: "report.risk_level == 'critical'"
      then: "require_human"
      approvers: ["architect", "security-lead"]

    - if: "report.evidence_bag.all_pass == false"
      then: "require_human"
      reason: "有证据项未通过"

    - if: "report.confidence.score >= 0.95 AND report.risk_level == 'low'"
      then: "auto_approve"

    - if: "report.confidence.score < 0.40"
      then: "auto_reject"
      reason: "置信度过低"

    - default: "require_human"
```

3. `PolicyGate.evaluate()` 的决策结果写入 `GateDecision` event。

4. 如果决策是 `require_human`，自动创建 HITL Approval 请求，approvers 从规则中获取。

#### 验收标准

- [ ] `EvidenceBasedPolicyGate` 根据规则做出决策
- [ ] `auto_approve` 条件满足时自动批准
- [ ] `auto_reject` 条件满足时自动拒绝
- [ ] `require_human` 时自动创建 HITL 审批，指定 approvers
- [ ] 默认规则（没有匹配时）为 `require_human`
- [ ] `tests/test_policy_gate_v2.py` 覆盖上述场景

## 三、不纳入 v0.9.0 的内容

| 项目 | 原因 |
|------|------|
| Architecture Delta **自动推断**（无 Planner 参与） | 需要静态分析 AST / 依赖图，独立大工程 |
| 实时 Evidence Dashboard（Web UI） | 前端工程，不在 Runtime Kernel 范围 |
| 跨 Goal 的趋势分析（"这个 Agent 最近 10 次的质量趋势"） | v0.10.0 |
| Contract Test 的自动生成与验证 | 依赖外部工具链成熟度 |
| GitHub PR 的原生集成 | 作为 A2A 适配器的一部分，v0.10.0 |
