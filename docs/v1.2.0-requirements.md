# Zelos v1.2.0 需求规格说明书

> 核心主题：**Runtime Diagnosis Engine** — Runtime 替 LLM 理解执行反馈、分类失败、做出工程决策。
>
> 参考文档：
> - `docs/blueprint/benchmark-plan.md` — 完整 Benchmark 计划
> - `docs/blueprint/swebench-strategy.md` — SWE-bench 策略分析

---

## 一、为什么要做 v1.2.0

### 现状（v1.1.0）

| 能力 | 状态 |
|------|------|
| Runtime Kernel（调度、重试、心跳、事件溯源） | ✅ |
| Governance Layer（Evidence、Confidence、PolicyGate） | ✅ |
| CP（Change Proposal）五元模型 | ✅ |
| Credential Management | ✅ |
| P0：并行 dispatch + Arbiter + Format Verifier | ✅ |

**但 SWE-bench 冲榜需要的 Runtime 诊断能力，一项都没做。**

### 核心洞察

>

\`\`\`
当前所有 SWE-bench Agent 的做法：
  Docker 跑测试 → stdout 原样贴给 Claude → Claude 自己读

Zelos v1.2.0 的做法：
  Docker 跑测试 → Diagnosis Engine 理解日志 → Failure Classifier 决策
  → Runtime 告诉 Fixer "这一行错了，期望X实际Y，值得修"
  或 "全量爆炸，放弃，切下一条候选"
\`\`\`

LLM 负责产生候选方案。Runtime 负责所有可以程序化完成的工程决策。

## 二、需求清单

### REQ-15：Diagnosis Engine（P0）

**背景**：当前 Agent 把 Docker 测试输出的 80KB+ 原始日志（含安装输出、构建噪声）原样传给 LLM。LLM 要从噪音里找信号，效率极低。Runtime 应该完成这一步。

**需求**：

1. 新增 `DiagnosisEngine` 类（`zelos/diagnosis_engine.py`）。
2. 输入：Docker 测试的原始 stdout/stderr 文本。
3. 输出：`DiagnosisResult` 结构化对象：

```python
@dataclass
class DiagnosisResult:
    total_tests: int
    passed: int
    failed: int
    errors: int
    pass_rate: float
    failures: list[FailureDetail]   # 每个失败测试的详情
    impact_scope: str               # "single_module" | "multi_module" | "full_explosion"
    recommendation: str             # "repair" | "abandon" | "retry"

@dataclass  
class FailureDetail:
    test_name: str                  # test_xxx
    failure_type: str               # AssertionError | TypeError | ImportError | ...
    expected: str | None            # 断言期望值
    actual: str | None              # 断言实际值
    location_file: str | None       # 出错文件
    location_line: int | None       # 出错行号
    traceback_summary: str          # 精简堆栈（最后3帧）
```

4. 解析策略：
   - pytest 输出：正则提取 `FAILED` 行 + `AssertionError` + traceback
   - unittest 输出：正则提取 `FAIL:` + `ERROR:` 行
   - 通用策略：`===== test session =====` 行提取总测试数/通过/失败

5. `impact_scope` 判定规则：
   - 失败数 ≤ 总测试数的 20% → `single_module`
   - 失败数 20%-50% → `multi_module`
   - 失败数 > 50% → `full_explosion`

6. `recommendation` 判定规则：
   - `full_explosion` → `abandon`
   - `single_module` + 全为 AssertionError → `repair`
   - `multi_module` → `retry`（再试一次）

**验收**：
- [ ] 真实 pytest 输出 → 正确提取 FAILED 测试数、失败类型、文件行号
- [ ] `full_explosion` 场景 → `recommendation = "abandon"`
- [ ] 空输出（全过）→ `failed=0, recommendation=None`
- [ ] `tests/test_diagnosis_engine.py` 覆盖 4 种场景

### REQ-16：Failure Classifier（P0）

**背景**：不是所有测试失败都值得修。Runtime 需要判定：修 / 重试 / 放弃。

**需求**：

1. 新增 `FailureClassifier` 类（`zelos/failure_classifier.py`）。
2. 输入：`DiagnosisResult`。
3. 输出：`ClassificationResult`：

```python
@dataclass
class ClassificationResult:
    action: str          # "repair" | "retry" | "abandon"
    reason: str          # 判定理由
    salvageable: bool    # 是否值得 Fixer 介入
    failure_type: str    # 主要失败类型
```

4. 分类规则表：

| 失败特征 | action | salvageable |
|---------|--------|-------------|
| `full_explosion`（>50% 失败） | `abandon` | False |
| 同一测试连续 3 轮失败 | `abandon` | False |
| 只有 `AssertionError` | `repair` | True |
| `TypeError` / `AttributeError` | `repair` | True |
| `ImportError` / `ModuleNotFoundError` | `repair`（尝试补依赖） | True |
| `Timeout` / `OOM` | `abandon` | False |
| 混合（Assertion + Import + 其他） | `retry` | True |

5. 与 Diagnosis Engine 的关系：`DiagnosisEngine` 提取结构化信息 → `FailureClassifier` 基于信息做决策。两个模块独立、可单独测试。

**验收**：
- [ ] 输入 `full_explosion` 诊断 → 输出 `abandon`
- [ ] 输入 `AssertionError` 诊断 → 输出 `repair, salvageable=True`
- [ ] 输入同一测试第 3 次失败 → 输出 `abandon`（止损）
- [ ] `tests/test_failure_classifier.py` 覆盖全部 7 种规则

### REQ-17：Runtime-Guided Repair（P1）

**背景**：当前 Agent 的"重试"是"从头生成 patch"。Zelos 的 Repair 是"Runtime 告诉 Fixer 错在哪一行、期望什么、实际什么，Fixer 定向修复"。

**需求**：

1. 新增 `RepairOrchestrator` 类（`zelos/repair_orchestrator.py`）。
2. 工作流：

```
DiagnosisResult（来自 REQ-15）
    │
    ▼
FailureClassifier（REQ-16）→ action="repair"
    │
    ▼
RepairOrchestrator
  ├── 构建 RepairContext：原始 issue + 当前 patch + 诊断结论
  ├── 调用 Fixer Agent（LLM）生成修复 patch
  ├── 重新评测（Docker）
  └── 重复最多 3 轮
```

3. `RepairContext` 包含：
   - 原始 issue 描述
   - 当前 patch 内容
   - 诊断结论（仅失败测试的结构化信息，不含原始日志）
   - 已尝试的修复方向列表（Hypothesis Tracker）

4. **Hypothesis Tracker**：Runtime 记录每次修复尝试的方向，避免 LLM 重复猜测：

```python
@dataclass
class HypothesisRecord:
    attempt: int
    hypothesis: str      # LLM 自述本次修复思路（一句话）
    result: str          # "still_failing" | "new_failures" | "passed"
```

5. 迭代上限 3 轮。第 3 轮仍失败 → `action = "abandon"`，切换并行池下一条候选。

**验收**：
- [ ] 输入诊断 → Fixer 生成修复 → 重新评测 → 全过则返回
- [ ] Hypothesis Tracker 记录每次尝试的方向
- [ ] 3 轮仍失败 → 正确 abandon
- [ ] `tests/test_repair_orchestrator.py` 覆盖上述场景

### REQ-18：Patch Ranking — 多因子评分（P2）

**背景**：当前 Arbiter 只做二值判定（过/不过）。多个候选都过了格式检查时，需要排名选优。

**需求**：

1. 新增 `PatchRanker` 类（`zelos/patch_ranker.py`）。
2. 评分因子：

| 因子 | 权重 | 高分 | 低分 |
|------|------|------|------|
| 修改文件数 | 0.25 | 1-3 个 | >10 个 |
| 修改 LOC | 0.20 | <50 行 | >500 行 |
| 是否修改测试 | 0.15 | 是 | 否 |
| 是否跨 package | 0.15 | 否 | 是 |
| 是否影响 issue 提及的模块 | 0.15 | 是 | 否 |
| 是否删除公开 API | 0.10 | 否 | 是 |

3. 评分公式：`score = Σ(weight × normalized_factor_score)`，输出 0-100。

**验收**：
- [ ] 输入 3 个候选 → 输出排名，最高分候选是修改量最小、最聚焦的那个
- [ ] `tests/test_patch_ranker.py` 覆盖评分逻辑
