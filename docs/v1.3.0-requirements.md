## 1. 版本背景：v1.2 留下了什么

### v1.2 已完成的

| 组件 | 文件 | 职责 |
|------|------|------|
| Diagnosis Engine | `zelos/diagnosis_engine.py` | pytest 输出结构化诊断，提取 file:line |
| Failure Classifier | `zelos/failure_classifier.py` | repair / retry / abandon 决策 |
| Repair Orchestrator | `zelos/repair_orchestrator.py` | Runtime-Guided Repair + Hypothesis Tracker |
| Patch Ranker | `zelos/patch_ranker.py` | 多因子候选排序 |
| Arbiter | `zelos/arbiter.py` | 并行 Agent 产出 first-to-pass-all 选择 |
| Contest Dispatch | `zelos/scheduler.py:schedule_contest()` | 同 Task → 多 Agent 并行派发 |

### v1.2 的核心问题

**不是功能不够，是验证顺序反了。** 12 个 Phase 全部加载、全部开启，但最底层的核心调度链路（Planner → Scheduler → Executor → Verifier）从未端到端验证过。

具体表现：

1. **Planner 是一次性的**——在执行前产出完整 Plan，执行中只在 Task 失败时被动响应。不支持"每一步执行后重新评估下一步做什么"。
2. **验证是后置的**——所有 Task 跑完才运行 Verifier Chain。一个明显的错误要等全部任务结束才被发现。
3. **没有 Feature Flag**——12 层组件全部加载，出问题时不知道是哪一层的问题。
4. **没有端到端实证**——SWE-bench v4 只跑了 17 题中的 6 题有效输出，分不清是 Planner 的问题、Scheduler 的问题、还是 Agent 的问题。
5. **Diagnosis Engine 是独立开发的**——功能正确，但没有嵌入核心闭环中验证。组件先于闭环，验证顺序反了。

### 架构反思的结论

参见 `docs/zelos-architecture-critique-and-evolution.md`。核心结论：

> **P0 最该做的事：用最薄的组件，跑通端到端的核心调度闭环。MPC 模式（每执行一步，用最新结果重新规划未来 N 步），Rule-based 重规划（Level 1）。**

---

## 2. v1.3 目标

v1.3 不做新功能。v1.3 做三件事：

### 目标 1：建立 Feature Flag 系统

让 12 层组件可以逐层开启/关闭，从核心向外围逐层验证。功能代码一行不动，只通过配置控制加载顺序。

### 目标 2：实现 MPC 自适应调度闭环

在 ExecutionEngine 的 Task 完成回调处插入 `replan_check` 钩子。默认使用 Rule-based 重规划规则（Level 1）。Planner 新增 `replan()` 方法。

### 目标 3：完成 SWE-bench 三组对比 PoC 实验设计

设计完整的实验方案：选 5 个 SWE-bench 题，每个用 3 种方式跑（基线 / +Runtime 诊断 / +编排）。定义测量指标、成功标准、数据收集方案。

**v1.3 完成后**，启动 PoC 实验执行（不在 v1.3 范围内，v1.3 只做到实验方案设计 + 核心闭环代码就绪）。

### REQ-02: MPC 自适应调度闭环

#### 背景

当前执行模型：

```
Planner 产出完整 Plan
  → Scheduler 按 DAG 顺序调度
    → Executor 逐个执行
      → 全部完成后 → Verifier Chain 验证
```

这是瀑布模型。问题是：
- Planner 在执行前就跑完了，执行中 Runtime 只在 Task 失败时介入
- 不会因为"置信度不够"主动插入补充验证
- 不会因为"中间结果暗示另一个方向更优"而切换策略
- 一个明显的错误要等全部任务跑完才被发现

#### 目标模型（MPC）

```
Planner 基于当前状态规划未来 N 步
  → Scheduler 派发第 1 步
    → Executor 执行
      → 增量验证（立即评估产出）
        → 决定：
          ✅ 通过 → 继续下一步
          ❌ 失败 → 触发 replan（只影响当前 Task 及下游）
          ⚠️ 置信度不足 → 插入补充验证 Task
        → 基于新状态重新规划未来 N 步
      → 循环
```

#### 需求

**REQ-02.1: replan_check 钩子**

在 `ExecutionEngine.submit_result()` 中，当 `FeatureFlags.mpc_replan == True` 时，Task 完成回调后执行 `replan_check`：

```python
# zelos/execution_engine.py

class ExecutionEngine:
    def __init__(self, ..., replan_rules: list = None):
        self._replan_rules = replan_rules or DEFAULT_REPLAN_RULES
        self._replan_callback = None  # Runtime 注入
        # v1.3.0: 维护当前 ExecutionPlan 引用（由 Runtime 设置）
        self._current_plan: "PlannerPlan | None" = None

    def set_replan_callback(self, callback):
        """Runtime injects: sync callback(plan_id, trigger, context) -> PlannerPlan | None"""
        self._replan_callback = callback

    def set_current_plan(self, plan: "PlannerPlan"):
        self._current_plan = plan

    def submit_result(self, task_id, agent_id, result):
        # ... existing logic (status transitions, event publishing) ...

        # v1.3.0: MPC replan check（仅当 Task 失败时触发）
        if (self._replan_callback and self._replan_rules
                and self._current_plan
                and result.get("status") != "completed"):
            artifact = result.get("artifact", {})
            verdict = self._run_incremental_verify(task_id, artifact)
            ctx = ReplanContext(
                task_id=task_id,
                artifact=artifact,
                verdict=verdict,
                current_plan=self._current_plan,
            )
            # v1.3.0: 收集完整失败上下文（含 Diagnosis 结果）
            diagnosis = self._run_diagnosis_if_applicable(task_id, result)
            for rule in self._replan_rules:
                if rule.should_replan(ctx):
                    new_plan = self._replan_callback(
                        plan_id=self._current_plan.plan_id,
                        trigger=rule.trigger_reason,
                        context={
                            "failed_task_id": task_id,
                            "verdict": verdict,
                            "diagnosis": diagnosis,  # ← DiagnosisResult (if available)
                            "completed_tasks": self._get_completed_task_ids(),
                            "failed_task": self._task_graph.get_task(task_id),
                        },
                    )
                    if new_plan:
                        self._current_plan = new_plan
                        self._event_bus.publish(Event(
                            event_id=str(uuid.uuid4()),
                            event_type="execution_plan.modified",
                            source="execution_engine",
                            timestamp=time.time(),
                            correlation_id=new_plan.plan_id,
                            payload={
                                "plan_id": new_plan.plan_id,
                                "trigger_reason": rule.trigger_reason,
                                "failed_task_id": task_id,
                                "replan_count": self._replan_count.get(
                                    new_plan.goal_id, 0
                                ),
                            },
                        ))
                    break
```

**设计决策**：`replan_check` 只在 Task **失败**时触发，而非每次 Task 完成后都触发。原因是：(1) 成功的 Task 不需要重规划；(2) 增量验证在成功时也运行，但只记录置信度，不触发 replan；(3) 这避免了"每一步都重新规划"的过度敏感问题。

**失败信息的三层传递链路：**

```
Task 失败 (result.status != "completed")
  │
  ├─→ 第 1 层：增量验证 (Verdict)
  │     verdict.result / verdict.confidence / verdict.reason
  │     → 回答："这个 Task 的即时产出是否合法？"
  │
  ├─→ 第 2 层：Diagnosis Engine (DiagnosisResult)  ← 仅当 result 含 test_output 时
  │     test_name / failure_type / file:line / expected vs actual / impact_scope
  │     → 回答："具体哪里错了？怎么错的？"
  │
  └─→ 第 3 层：Failure Classifier (ClassificationResult)  ← 仅当 Diagnosis Engine 产出后
        action: repair|retry|abandon / salvageable / failure_type
        → 回答："还值得修吗？怎么修？"

三层信息打包为 failure_context → 传给 Runtime._on_replan() → 传给 Planner.replan_path()
  → Planner 在生成新 Task 时，将诊断细节写入 Task.description
  → 下游 Agent 收到的不再是 "fix the bug"，而是 "fix AssertionError at tests/foo.py:42, expected X got Y"
```

`ExecutionEngine` 新增诊断触发方法：

```python
def _run_diagnosis_if_applicable(self, task_id: str, result: dict) -> "DiagnosisResult | None":
    """
    如果 task result 中包含 test_output，运行 Diagnosis Engine。
    仅在 FeatureFlags.diagnosis_engine == True 时调用。
    """
    test_output = result.get("test_output") or result.get("error", {}).get("test_output", "")
    if not test_output or not self._diagnosis_engine:
        return None
    return self._diagnosis_engine.diagnose(test_output)
```

**REQ-02.2: Runtime.replan() 协调方法**

重规划逻辑在 `ZelosRuntime` 中实现（而非 Planner 内部），因为需要协调 Scheduler、TaskGraphEngine 和 Planner 三个组件：

```python
# zelos/runtime.py 新增方法

class ZelosRuntime:
    def _on_replan(self, plan_id: str, trigger: str, context: dict) -> "PlannerPlan | None":
        """
        Runtime 级别的重规划协调。
        由 ExecutionEngine 的 replan_callback 调用。

        步骤：
        1. 标记失败 Task 及其下游为 BLOCKED（操作 TaskGraphEngine）
        2. 调用 Planner 为被阻塞路径生成替代 Task
        3. 将新 Task 插入 TaskGraphEngine，更新 Plan
        4. 返回更新后的 PlannerPlan
        """
        task_graph = self._task_graph
        failed_task_id = context["failed_task_id"]
        verdict = context.get("verdict")

        # 1. 找到当前 Plan 中失败 Task 的下游依赖
        downstream_ids = task_graph.get_dependents(failed_task_id)
        for tid in downstream_ids:
            task = task_graph.get_task(tid)
            if task and task.status not in (
                TaskStatus.COMPLETED, TaskStatus.FAILED, TaskStatus.FATAL_FAILED
            ):
                task_graph.transition(tid, TaskStatus.BLOCKED)

        # 2. 构建结构化失败上下文，调用 Planner 生成替代路径
        goal = self._goals.get(plan_id, {}).get("goal")
        failure_context = self._build_failure_context(
            failed_task_id=failed_task_id,
            context=context,
        )
        replacement_tasks = self._planner.replan_path(
            goal=goal,
            failed_task_id=failed_task_id,
            failure_context=failure_context,
            completed_tasks=context.get("completed_tasks", []),
        )

    def _build_failure_context(self, failed_task_id: str, context: dict) -> dict:
        """
        构建结构化失败上下文，传给 Planner.replan_path()。

        包含三层信息（从粗到细）：
        1. verdict — 增量验证的即时判断（passed/failed/confidence）
        2. diagnosis — Diagnosis Engine 的结构化诊断（file:line, expected vs actual）
        3. classification — Failure Classifier 的工程决策（repair/retry/abandon, salvageable）
        """
        fc = {
            "failed_task_id": failed_task_id,
            "verdict": {
                "result": context["verdict"].verdict,
                "confidence": context["verdict"].confidence,
                "reason": getattr(context["verdict"], "reason", ""),
            },
        }

        # 如果 Diagnosis Engine 可用并已运行，附带结构化诊断
        diagnosis = context.get("diagnosis")
        if diagnosis:
            fc["diagnosis"] = diagnosis.to_dict()
            fc["diagnosis"]["failures_detail"] = [
                {
                    "test_name": f.test_name,
                    "failure_type": f.failure_type,
                    "location": f"{f.location_file}:{f.location_line}",
                    "expected": f.expected,
                    "actual": f.actual,
                }
                for f in diagnosis.failures[:5]
            ]

        # 如果 Failure Classifier 可用，附带分类决策
        if self._flags.failure_classifier and diagnosis:
            classification = self._failure_classifier.classify(diagnosis)
            fc["classification"] = {
                "action": classification.action,
                "reason": classification.reason,
                "salvageable": classification.salvageable,
                "failure_type": classification.failure_type,
            }

        return fc

        # 3. 将新 Task 插入 TaskGraphEngine
        for rt in replacement_tasks:
            task = Task(
                task_id=rt.task_id,
                plan_id=plan_id,
                description=rt.description,
                required_capability=rt.required_capability,
                dependencies=rt.dependencies,
            )
            task_graph.add_task(task)

        # 4. 更新 PlannerPlan
        plan = self._get_plan(plan_id)
        for rt in replacement_tasks:
            plan.tasks.append(rt)
        plan.version += 1
        return plan
```

**REQ-02.4: Planner.replan_path() 方法**

> **注意**：当前代码中 `LLMPlanner` 没有继承自任何 Planner 基类。v1.3 需要创建一个 `Planner` 基类（`zelos/planner.py`），`LLMPlanner` 改为继承它。`replan_path()` 是基类方法（有默认实现，子类可覆盖）。

```python
# zelos/planner.py 新增

class Planner(ABC):
    """Base class for all Planners. v1.3.0: extracted from LLMPlanner."""

    @abstractmethod
    def plan(self, goal, context: dict) -> PlannerPlan:
        """Generate an execution plan for a goal."""
        ...

    def replan_path(
        self,
        goal,
        failed_task_id: str,
        failure_context: dict,
        completed_tasks: list[str],
    ) -> list["PlannerTask"]:
        """
        为失败的路径生成替代 Task。

        failure_context 包含结构化失败信息（不是字符串）：
        {
            "verdict": {"result": "failed", "confidence": 0.3, "reason": "..."},
            "diagnosis": {                    # Diagnosis Engine 输出（如有）
                "failures_detail": [
                    {"test_name": "...", "failure_type": "AssertionError",
                     "location": "tests/foo.py:42", "expected": "X", "actual": "Y"}
                ],
                "impact_scope": "single_module",
                "recommendation": "repair"
            },
            "classification": {               # Failure Classifier 输出（如有）
                "action": "repair",
                "reason": "Salvageable: AssertionError, 1 failures in single_module",
                "salvageable": true,
                "failure_type": "AssertionError"
            }
        }

        默认实现：生成一个同 Capability 的新 Task，并将 diagnosis 信息
        注入到 Task description 中（让下游 Agent 知道具体哪里错了）。
        LLM Planner 可以覆盖此方法，用完整诊断上下文重新分解。
        """
        diag = failure_context.get("diagnosis", {})
        classification = failure_context.get("classification", {})

        # 构建富含诊断信息的 Task description
        desc_parts = [f"Previous attempt failed. Reason: {classification.get('reason', 'unknown')}"]
        for f_detail in diag.get("failures_detail", []):
            desc_parts.append(
                f"  FAILED: {f_detail['test_name']} — {f_detail['failure_type']} "
                f"at {f_detail['location']}"
            )
            if f_detail.get("expected"):
                desc_parts.append(f"    Expected: {f_detail['expected']}")
            if f_detail.get("actual"):
                desc_parts.append(f"    Actual: {f_detail['actual']}")

        return [PlannerTask(
            task_id=str(uuid.uuid4()),
            description="\n".join(desc_parts),
            required_capability=self._infer_capability(failed_task_id),
            dependencies=self._infer_dependencies(failed_task_id, completed_tasks),
        )]

class LLMPlanner(Planner):
    """LLM-based planner. Now extends Planner base class."""
    # ... existing code unchanged, inherits replan_path() ...
```

**REQ-02.5: Replan 上限**

重规划次数必须有上限，防止无限循环：

```python
DEFAULT_MAX_REPLANS = 5

class ExecutionEngine:
    def __init__(self, ..., max_replans: int = DEFAULT_MAX_REPLANS):
        self._max_replans = max_replans
        self._replan_count: dict[str, int] = {}  # goal_id → count

    def _replan_check(self, ...):
        goal_id = self._current_plan.goal_id
        count = self._replan_count.get(goal_id, 0)
        if count >= self._max_replans:
            self._event_bus.publish(GoalFailed(
                goal_id=goal_id,
                reason=f"Exceeded max replans ({self._max_replans})",
            ))
            return
        self._replan_count[goal_id] = count + 1
        # ... proceed with replan
```

**REQ-02.6: Replan 审计**

每次重规划必须发布 `ExecutionPlanModified` Event，包含：
- `plan_id`: 新 Plan 的 ID
- `trigger_reason`: 触发规则名称（如 "VerdictRejectedRule"）
- `failed_task_id`: 导致重规划的 Task
- `replan_count`: 当前 Goal 的第几次重规划
- `old_path_summary`: 被放弃路径摘要
- `new_path_summary`: 新路径摘要

#### 验收标准

- [ ] ExecutionEngine 在 Task 完成后调用 `replan_check`
- [ ] Planner.replan() 返回合法的 ExecutionPlan（DAG 拓扑不变）
- [ ] 重规划超过 5 次 → Goal FAILED (FATAL)
- [ ] 每次重规划发布 `ExecutionPlanModified` Event
- [ ] `FeatureFlags.mpc_replan = False` 时完全不触发重规划逻辑
- [ ] 单元测试覆盖：正常完成不触发 / 单次触发 / 多次触发 / 上限触发

### REQ-03: 增量验证（Incremental Verification）

#### 背景

当前 `VerifierChain` 是后置验证——所有 Task 完成后一次性执行。v1.3 需要将验证前置到每一步产出后。

#### 需求

**REQ-03.1: 增量验证钩子**

在 ExecutionEngine 的 `submit_result()` 中，Task 完成后立即运行轻量级验证：

```python
class ExecutionEngine:
    def _run_incremental_verify(self, task_id: str, artifact: dict) -> Verdict:
        """Run lightweight verification on a single task's output."""
        verifier = self._incremental_verifier
        if not verifier:
            return Verdict(verdict="passed", confidence=1.0)

        # 轻量验证：只检查 artifact 非空 + 基本 schema
        # 不检查代码质量（那是 VerifierChain 的职责）
        if artifact is None or (isinstance(artifact, dict) and not artifact):
            return Verdict(verdict="failed", confidence=0.0,
                          reason="Empty artifact")

        task = self._task_graph.get_task(task_id)
        rules = ["non_empty"]
        if task and hasattr(task, 'expected_output_schema') and task.expected_output_schema:
            rules.append("schema")

        criteria = VerificationCriteria(
            expected_output_schema=getattr(task, 'expected_output_schema', {}),
            rules=rules,
        )
        return verifier.verify(artifact, criteria)
```

**Task 新增字段**：`Task` dataclass 新增 `expected_output_schema: dict | None = None`，允许 Planner 在生成 Task 时指定期望的产出格式。此字段可选——如果为 None，增量验证只检查 non_empty。

**REQ-03.2: 后置验证向后兼容**

`VerifierChain` 保留不动。增量验证是新增的、在每一步后运行的轻量验证。后置全量验证在 `FeatureFlags.verifier_chain == True` 时仍然运行。

区别：

| 维度 | 增量验证 | 后置验证（VerifierChain） |
|------|---------|--------------------------|
| 触发时机 | 每个 Task 完成后立即 | 所有 Task 完成后 |
| 验证范围 | 单个产出 | 全局一致性 |
| 验证内容 | schema / non_empty / 基础规则 | code_review / security / 全量 |
| 失败行为 | 触发 replan | FAIL-stop + 重规划 |

**REQ-03.3: 验证结果发布为 Event**

```python
@dataclass
class ArtifactVerified(Event):
    task_id: str
    verdict: str        # passed | failed | uncertain
    confidence: float
    verifier_name: str
    reason: str
```

#### 验收标准

- [ ] 每个 Task 完成后自动运行增量验证
- [ ] 增量验证失败 → 触发 replan_check
- [ ] `FeatureFlags.mpc_replan = False` 时增量验证仍然运行（只是不触发 replan）
- [ ] 后置 VerifierChain 在增量验证之后仍可运行（不冲突）
- [ ] 验证结果 Event 包含 task_id / verdict / confidence / reason

### REQ-04: Replan 规则引擎

#### 背景

MPC 重规划需要明确的触发条件。v1.3 使用 Rule-based 方法（Level 1）。

#### 需求

**REQ-04.1: 默认规则集**

```python
# zelos/replan_rules.py

from abc import ABC, abstractmethod
from dataclasses import dataclass

@dataclass
class ReplanContext:
    task_id: str
    artifact: dict
    verdict: "Verdict"
    current_plan: "ExecutionPlan"


class ReplanRule(ABC):
    @property
    @abstractmethod
    def trigger_reason(self) -> str:
        """Human-readable trigger description."""
        ...

    @abstractmethod
    def should_replan(self, ctx: ReplanContext) -> bool:
        ...


class VerdictRejectedRule(ReplanRule):
    """Verifier returned rejected → replan."""
    trigger_reason = "verdict_rejected"

    def should_replan(self, ctx: ReplanContext) -> bool:
        return ctx.verdict.verdict == "failed"


class ConfidenceLowRule(ReplanRule):
    """Verifier confidence below threshold → insert supplementary verification."""
    trigger_reason = "confidence_low"

    def __init__(self, threshold: float = 0.5):
        self.threshold = threshold

    def should_replan(self, ctx: ReplanContext) -> bool:
        return ctx.verdict.confidence < self.threshold


class SchemaMismatchRule(ReplanRule):
    """Artifact schema doesn't match expected output schema → replan."""
    trigger_reason = "schema_mismatch"

    def should_replan(self, ctx: ReplanContext) -> bool:
        task = ctx.current_plan.get_task(ctx.task_id)
        if not task or not getattr(task, 'expected_output_schema', None):
            return False
        artifact_type = type(ctx.artifact).__name__
        expected_type = task.expected_output_schema.get("type", "")
        return artifact_type != expected_type


class EmptyArtifactRule(ReplanRule):
    """Artifact is empty or None → replan."""
    trigger_reason = "empty_artifact"

    def should_replan(self, ctx: ReplanContext) -> bool:
        return ctx.artifact is None or (
            isinstance(ctx.artifact, dict) and not ctx.artifact
        )


DEFAULT_REPLAN_RULES = [
    VerdictRejectedRule(),
    ConfidenceLowRule(threshold=0.5),
    SchemaMismatchRule(),
    EmptyArtifactRule(),
]
```

**REQ-04.2: 可扩展**

规则引擎支持自定义规则。开发者可以：

```python
class MyCustomRule(ReplanRule):
    trigger_reason = "my_custom_trigger"

    def should_replan(self, ctx: ReplanContext) -> bool:
        return "TODO" in str(ctx.artifact)


runtime = ZelosRuntime(config={
    "features": {"mpc_replan": True},
    "replan_rules": DEFAULT_REPLAN_RULES + [MyCustomRule()],
})
```

#### 验收标准

- [ ] 4 条默认规则全部实现
- [ ] 每条规则可独立开启/关闭
- [ ] 支持注册自定义规则
- [ ] 多条规则同时满足时，只触发第一条（短路）
- [ ] 每条规则触发时 `trigger_reason` 记录在 Event 中

## 4. 实验设计：三组对比验证核心假设

### 4.1 核心假设

> **H₁: Runtime 编排多 Agent 的 SWE-bench 任务成功率，高于任何单体 Agent 单独执行。**

> **H₂: Runtime 的诊断和决策能力（Diagnosis Engine + Failure Classifier + Repair Orchestrator）比 Agent 自己读日志做决策更省 Token。**

### 4.2 实验分组

选 5 个 SWE-bench 题，每个分别用 3 种方式跑：

| 分组 | 做法 | 要验证的假设 |
|------|------|-------------|
| **基线组** | live-SWE-agent 原生单打（1 个 Agent 从头做到尾） | "最好的单体 Agent 能拿多少分" |
| **+Runtime 诊断组** | live-SWE-agent 通过 Zelos Adapter 执行（单 Agent），Runtime 在 Agent 产出 patch 后运行测试，用 Diagnosis Engine + Failure Classifier + Repair Orchestrator 自动分析失败原因并定向修复。Agent 本身不读测试日志——日志由 Diagnosis Engine 结构化解析后，只将诊断结论传给 Agent | "Runtime 的诊断和决策能力是否比 Agent 自己读日志更好" |
| **+编排组** | Task 拆成定位/生成/审查三步，分别用不同 Capability 的 Agent（如 live-SWE-agent 定位 + Claude Code 生成 + Reviewer Agent 审查），中间 Runtime 做 MPC 决策。**注意**：三组使用相同**质量梯队**的 Agent（都是 SWE-bench 排行榜前列的），但编排组中不同步骤可能使用不同 Agent——这是编排的天然优势，而非变量混淆 | "Runtime 编排多 Agent 是否比任何单体 Agent 更好" |

### 4.3 测量指标

| 指标 | 意义 | 计算方法 |
|------|------|---------|
| **是否通过** (pass/fail) | 最终成功率：patch 通过全部测试 | SWE-bench eval 标准判定 |
| **重试次数** | 无效重试越少越好 | 计数：Agent 重试 + Runtime replan 次数 |
| **Token 消耗** | Runtime 的诊断是否比全量日志丢给 LLM 更省 Token | 各组总 Token（LLM API 返回的 usage） |
| **Runtime 决策触达率** | MPC Verifier/Replan 是否实际被触发了（没触发说明场景太简单） | 触发了决策的 Task 数 / 总 Task 数 |
| **决策后验准确率** | 触发了的决策事后看对不对 | 事后人工判定：每个 replan 决策是否正确 |

### 4.4 数据收集格式

每个实例的每组实验产出一个 JSON：

```json
{

  "group": "orchestrated",
  "timestamp": "2026-08-10T14:30:00Z",
  "result": {
    "pass": true,
    "patch": "...",
    "total_time_seconds": 342
  },
  "metrics": {
    "retry_count": 2,
    "replan_count": 1,
    "total_tokens": 125000,
    "token_breakdown": {
      "planner": 5000,
      "search_agent": 30000,
      "fix_agent": 60000,
      "review_agent": 20000,
      "runtime_overhead": 10000
    },
    "decisions": [
      {
        "step": 3,
        "type": "replan",
        "trigger": "confidential_low",
        "old_path": "fix_attempt_1",
```

### 4.5 结果判断标准

如果"编排组"比"基线组"好——哪怕只好了 2 题——就证明了核心假设：

```
Pass rate:
  基线组:         X/5
  +Runtime诊断组:  Y/5
  +编排组:        Z/5

如果 Z > X: "Runtime 编排多 Agent 比单体 Agent 更好" ✅
如果 Y > X: "Runtime 诊断能力有边际改善" ✅
如果 Z > Y: "编排的增量价值超过单纯诊断" ✅
```

### 4.6 有效性威胁

| 威胁 | 类型 | 缓解 |
|------|------|------|
| 样本量小 (n=5) | 外部有效性 | 这是 PoC，不是学术论文。5 题的定性结论足够决定下一步方向 |
| Agent 能力差异 | 内部有效性 | 三组使用相同质量梯队的 Agent（都是 SWE-bench 排行榜前列）。编排组中不同步骤可能使用不同 Agent——这恰是编排的优势（每个步骤用最合适的 Agent），不是变量混淆。额外控制：记录每个步骤使用的具体 Agent，便于事后追踪能力差异的影响 |
| 网络/Tool 调用波动 | 内部有效性 | 每组跑 2 次，取较好的成绩（模拟真实最优配置） |
| 实验者偏差 | 构造有效性 | 实例选择标准预先定义，不事后挑选 |
| Runtime 诊断组的 Adapter 开销 | 内部有效性 | 在 Token 消耗指标中单独拆出 `runtime_overhead`，区分 Runtime 开销 vs Agent 开销 |

## 7. 风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| Planner.replan() 产出的 Plan 不合法（破坏 DAG 拓扑） | 中 | 高 | 添加 `PlanValidator` 在 replan 后校验 DAG |
| MPC 环路在复杂场景下不收敛（反复 replan） | 中 | 中 | 5 次上限 + 逐次增加 backoff |
| 增量验证太轻量，漏掉真实问题 | 低 | 中 | 保留 VerifierChain 作为后置补充 |
| Stage A 模式下的 Runtime 缺失必要依赖 | 低 | 高 | 充分的单元测试 + 集成测试在 stage_a 模式下运行 |
| PoC 实验的 3 组结果差异不显著 | 中 | 中 | 这是可能的科学结论——如果编排不比单体好，知道这个也一样有价值 |

### 未知风险

**MPC 模式的核心风险不是工程实现，而是 Planner 是否能在"只有部分信息时"做出比"一次性全量规划时"更好的决策。** 如果 Planner 在信息不完整时的决策质量低于信息完整时的一次性规划，MPC 可能反而降低成功率。

验证方法：在同一个端到端案例上，分别用 MPC（replan 开启）和一次性规划（replan 关闭）跑，对比最终产出质量。如果 MPC 更差，需要在 P0.5 引入 Confidence-weighted 决策（Level 2），让 Planner 在置信度不足时选择"不做决定、先收集更多信息"。
