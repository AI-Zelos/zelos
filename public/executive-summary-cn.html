论文摘要（供领导层审阅）

两篇定义 AI 原生软件工程的奠基性论文。一篇提供了形式化理论，一篇提供了可落地的工程工作流。

论文一：Beyond Code — AI 原生范式的软件工程形式化理论

一句话：AI 不只改变了怎么写代码——它从形式化、数学层面改变了"软件工程"本身的定义。

核心论点

传统软件工程是为"人写代码、人审查代码"的世界设计的。这个世界正在终结。当 AI 每小时产出 35,000+ 行代码，而人的阅读速度约为每小时 200 行时，瓶颈已经转移。不再是代码生产速度，而是信任。

本文用数学方式形式化了这一转变：

  • 11 条定理，严格证明了以代码审查为核心的流程在 AI 驱动的开发速度下无法线性扩展
  • 形式化理论表明：软件工程的基本单元正从"代码"转向"变更"——运行时的职责是证明可信性，而非执行指令
  • "Subject-Decoupled Credibility Law（主体解耦可信定律）"：验证必须与执行分离，信任才能规模化

为什么老板应该关心

每个技术管理者都在问："AI 写的代码越来越多，我们怎么治理？"这篇论文提供了这个问题的理论基础。它不是一篇观点文章——它构建了严格的数学论证，证明这种转变是不可避免的，并提供了讨论它的词汇体系（Intent / Evidence / Confidence / Verdict / 意图 / 证据 / 置信度 / 裁决）。

投稿目标：ICSE / FSE（SEIP 轨道）、ASE。这篇论文具备"Editor's Pick"的特质——用形式化严格性挑战了一个 50 年历史的范式。

论文二：从 PR 到 CP — 面向 AI 大规模开发的新型软件变更治理流程

一句话：GitHub PR 是为人类写 200 行变更设计的。当 AI 写 20,000 行变更时，我们需要根本性的替代方案。这就是。

核心方案

CP（Change Capsule，变更提案） — Pull Request 的替代品，从零开始为 AI 时代设计。

传统 PR Change Capsule（CP）
代码是核心制品 变更意图 + 证据是核心
代码写完之后再审查 代码生成前先锁定约束
人必须逐行阅读 人看置信度分数 + 证据摘要
"看起来没问题" "置信度 97%。证据：47/47 测试通过。安全扫描：PASS。性能：TPS 提升 31.8%。"
无需回滚方案 回滚方案强制要求

实验结果（20 个任务，单一变量对照）

指标 传统 PR CP（本文方案） AI 辅助 PR
返工率 35% 5% 20%
约束违规率 30% 0% 15%
人工依赖度 100% 0% 100%
人均耗时/任务 11.7 分钟 3.2 分钟（省 73%） ~10 分钟

核心发现：AI 辅助 PR（AI 预审代码，人做最终审批）仍然有 100% 的人工依赖度。瓶颈是拓扑性的——PR 的"生成→评审→合并"链路无论用什么工具，人工评审始终在关键路径上。CP 修的是拓扑，不是工具。

为什么老板应该关心

这直接回答了每个 CTO 在问的问题："如果 AI 写代码，谁来审查？"答案是：没有人逐行读。运行时验证变更，呈现证据。 73% 的时间压缩是真实数据，不是估算。

论文还包含形式化证明（3 条命题），证明 PR 无法通过增量改进演进为 CP——它们是结构性异构的范式。这不是 PR 的增强版。这是替代品。

投稿目标：ICSE 2027 / FSE 2027（SEIP 轨道）、ASE 2027。强工业相关性 + 严格的形式化支撑。

两篇论文的关联逻辑

论文一（Beyond Code）构建了理论基础：为什么旧范式会崩塌，新范式必须长什么样。

论文二（从 PR 到 CP）构建了工程实现：一个具体的、可度量的、真正跑通了的 Pull Request 替代方案。

两者构成完整论证链：

理论（论文一）：代码审查在 AI 时代数学上不可扩展

    ↓
